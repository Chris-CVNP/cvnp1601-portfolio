Week 12 Break/Fix Diagnosis

State
The crontab -l listing confirms the PATH line and daily 0 6 * * * entry are properly formatted; therefore, the job remains scheduled. However, the ls -la listing only lists one report file; this report file was created July 18 at 06:00; therefore, nothing new has been saved since this run. According to the date command, the current time is Wed Jul 22 09:14:02 UTC. This indicates four days of scheduled runs have elapsed with no new report. The ps listing displays PIDs 4821 and 4822; PID 4821 is a copy of health_report.sh; PID 4821 has been active for three days, three hours, and fourteen minutes. PID 4822 represents vmstat 1 and has been active one second less than PID 4821. Working backwards from the present time, both processes began on Jul 19 at 06:00. At this point it was the first run since the last valid report. Once it began it ran indefinitely.

Root Cause
vmstat is called with a delay but no count. When vmstat is provided a delay but no count, it continues producing samples indefinitely; therefore, once it is started it continues until it is manually interrupted. The script pauses until vmstat finishes before continuing to produce the rest of the report; therefore, since it was started on Jul 19 at 06:00 it has continued to run indefinitely leaving no opportunity to create a new report. Although the PATH line was suspected as contributing to this problem, based upon the fact that cron successfully initiated the script as evidenced by the currently running process, it is clear this was not the problem.

Remediation
The first action is to terminate the run of vmstat and health_report.sh using kill 4822 4821. This will send SIGTERM to vmstat and health_report.sh. Next confirm both processes are terminated using ps -eo pid,etime,cmd | grep health_report. Finally modify the vmstat line in /home/student/scripts/health_report.sh from vmstat 1 to vmstat 1 5 so that it produces five samples and then terminates. To perform this modification find the line containing vmstat using grep -n vmstat /home/student/scripts/health_report.sh. Use nano to modify this line to vmstat 1 5.

Verification
There are two aspects to verifying this remediation. The first aspect involves confirming that the remediated version of health_report.sh performs as expected under normal operating conditions. Perform this verification by executing bash /home/student/scripts/health_report.sh. It should complete quickly and return to the prompt. Next confirm no copy of health_report.sh remained active by performing a ps -eo pid,etime,cmd | grep health_report. The second aspect is validating that remediated version of health_report.sh creates a valid report after execution. Perform this validation after the next 6:00 AM run by performing a ls -la ~/reports. A new report file should exist in your reports directory with today's timestamp. Additionally verify that your remediated version of health_report.sh produced a valid report by viewing this file with tail -80. Your new report file should include all required sections including Listening Services and contain five samples produced by vmstat. Lastly verify your remediated version of health_report.sh did not produce any errors during execution by viewing the most recent entries in health_cron.log with tail -40 ~/reports/health_cron.log.

Security Note
A monitoring script that silently stops producing reports is a reliability blind spot as long as the crontab appears to be configured normally and an alert is not triggered. Because everyone assumes that their servers are checked daily via automated reporting, nobody knows that for four days nothing has been reported about them. If disk space had filled or if a service had crashed over those four days, nobody would have known and only looking at the July 18 report would give anyone a false sense of security. False confidence caused by lack of reporting is far worse than not having any form of automated reporting because someone would have had to investigate manually and discovered something wrong with their server.
