What went wrong or could have gone wrong
Initially, neither Docker nor any part of it was even installed on the lab VM so the Task 1 baseline commands gave me a command not found message at first. The install for Docker also failed due to a partially-configured host nginx package that was from a previous lesson that had server_nmae instead of server_name on line 46 of /etc/nginx/sites-enabled/default.
In my original installs for Docker, I also forgot to include the apt install docker-ce command which resulted in the non-existence of the docker group and I couldn't add myself to the group via usermod and got the message group docker does not exist.
What evidence I checked first
The first things I checked were the results of the commands command -v docker and groups. They both showed no binary for docker and no group named docker. After apt failed, I looked at the error messages produced by apt during its failure, they said something about failing a configuration test for an unknown directive called server_nmae at line 46 in nginx's config. After discovering that Docker hadn't been installed after my first try, I went back and reviewed my entire terminal session and realized that after doing the second apt update I went straight into trying to use usermod without going thru the install process in between the two operations.
What I tried
Instead of installing the Docker Engine from the Ubuntu docker.io package, I decided to install from Docker's official apt repo. I then used sed to correct the nginx typo using the --follow-symlinks option to make sure the symlinked site file stayed a link. I then ran nginx -t to see if the config would pass before finishing up the aborted pkg init process with dpkg --configure -a. By now, I'd finally run the apt install that I'd missed, gotten my user added to the just-created docker group and done a full reboot to let my new group membership happen as well as let the pending kernel upgrade happen.
What fixed it
Fixing the nginx typo caused the blocked packages to unblock and running the install step that I'd skipped allowed Docker Engine 29.10.0 to get installed on my machine as well as create the docker group. With the reboot, all of Task 1 commands worked perfectly and didn't require me to run them with sudo, as specified in the task list.
How I verified the result
docker --version came back with Docker version 29.10.0, docker ps and docker images worked w/o any permission errors, and ss confirmed port 8080 was available on the host. I also used docker ps to confirm the container was started several times during different parts of testing: docker ps showed it as Up along with 0.0.0.0:8080->80/tcp, I used curl -I http://localhost:8080 to show that I was receiving an HTTP/1.1 200 OK status code and I captured the request into docker logs as well. All three of these tests were successful after I ran docker restart and after docker stop/docker start.
Security and reliability impact
A corrupted package left in a partially configured state prevents any future apt-based updates on the host, including security updates, therefore while it may seem superficially cosmetic, the typo left over from an earlier lesson represented a legitimate reliability risk. In addition, adding my user to the docker group provides my user account with root-level access to the host through the Docker socket, which is acceptable on a single-user lab VM however should be restricted to trusted admins in production. Exposed services through published ports are also able to bypass host firewalls therefore those port mappings need to be documented and vetted similar to any other exposed service.
