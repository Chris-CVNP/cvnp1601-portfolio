# Troubleshooting Narrative

the command line path was an issue. In the guides example, /bin/systemctl was used. I may have just put this path into my sudoers file without thinking, rather than using the path my own system reported. The assignment directs you to find the path with which systemctl and use that one. I also encountered another problem while testing. The command provided by the assignment to test if devuser has access to the privileges he has assigned him was refused.

To determine the real path for the systemctl command, I queried the system. So I tried running which systemctl. It didn't return anything. This told me that the command, or specifically systemctl wasn't resolving properly in my PATH environment variable. To figure out why the nested sudo -l command was denied, I looked at the actual message denying his request. According to the message, devuser isn't allowed to run /usr/bin/sudo as devuser.

I then ran which systemctl again, and this time it returned /usr/bin/systemctl. I put that path into the rule. I changed methods regarding the denied nested sudo -l command, and instead entered the shell as devuser using sudo -u devuser bash and ran sudo -l separately instead of nested.

Both of these modifications fixed the issues. The rule now correctly matches on the proper path for the systemctl command. Running sudo -l from inside devuser's shell showed me all of devuser's privileges (as requested).

I checked things from two perspectives. I ran sudo visudo -c, which checks /etc/sudoers for syntax problems. I got back a positive response indicating that /etc/sudoers had valid entries. Second, I verified the functionality as devuser. After entering devuser's shell with sudo -u devuser bash, I executed the commands described above. Executing sudo /usr/bin/systemctl restart nginx prompted for no password, executing systemctl status nginx displayed information showing that nginx had started successfully, and executing sudo /usr/bin/systemctl stop nginx prompted for authentication and was subsequently denied. Lastly, sudo -l shows you which commands a user is permitted to execute and I verified that there was exactly one permitted command.

A path problem would have occurred silently. visudo only checks that a rule is syntactically valid; it does not confirm that the command in the rule is the one the user will actually invoke. The only way to know the grant works is to run the allowed command and watch it succeed. The other, refused sudo -l, represented the opposite behavior: it demonstrated that the policy functioned as expected. Asking sudo to run its own sudo binary as devuser with sudo -u devuser sudo -l attempts to ask sudo to run the sudo binary itself as devuser, and devuser is only permitted one command, which is not sudo. The refusal to allow execution demonstrates that devuser's permissions were defined tightly and correctly, rather than being a problem to resolve.
