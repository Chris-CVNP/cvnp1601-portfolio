## Steps Taken

### Step 1. Write disk_report.sh

Create the scripts and logs directories:

```
mkdir -p ~/scripts ~/logs
```

Write the script:

```

```

Make it executable:

```
chmod +x ~/scripts/disk_report.sh
```

Run it manually:

```

```

Show the log:

```

```

**Expected output includes:** no terminal output from the manual run, since the script writes only to its log, and a log entry with Disk Report Start, the df -h table, and Disk Report Complete, all stamped with the same run time.

**Status:** Complete. Evidence: screenshots/01-manual-run-log.png.

### Step 2. Schedule with cron using absolute paths

Open the crontab and choose nano at the editor prompt:

```
crontab -e
```

Test schedule line added in the editor:

```
*/2 * * * * /home/[username]/scripts/disk_report.sh >> /home/[username]/logs/disk_report_cron.log 2>&1
```

Confirm the test schedule saved:

```
crontab -l
```

After at least two scheduled runs, open the crontab again:

```
crontab -e
```

Final schedule line that replaced the test line:

```
0 6 * * 0 /home/[username]/scripts/disk_report.sh >> /home/[username]/logs/disk_report_cron.log 2>&1
```

Confirm the final schedule saved:

```
crontab -l
```

**Expected output includes:** crontab: installing new crontab after each save, the */2 line in the first crontab -l, and only the 0 6 * * 0 line in the second.

**Status:** Complete with a deviation. The paths use my own home directory instead of /home/student. See Issue 1. Evidence: screenshots/02-test-schedule.png and screenshots/03-final-schedule.png.

Cron jobs should use absolute paths since cron will not start your job in your home directory nor will it create an environment for you to run in with all the variables that are available when you manually login. Therefore, if your script uses a relative path, this could result in the job looking for files somewhere completely different than you intended. Also, if the job runs but fails there may be no indication on the screen that something has gone wrong. With the 2>&1 redirection, both standard output and standard error are directed to the same place, thus allowing me to review errors generated by the failure of the job rather than them being lost forever in the local mail spool. If you do not include this redirection then it would be difficult to tell whether or not a run was successful or unsuccessful. A successful run and an unsuccessful run could look identical since each results in nothing left behind to verify what actually happened.

### Step 3. Verify scheduled execution

## Troubleshooting Notes

### Issue 1: The assignment's crontab paths do not exist on my VM

**Incorrect command:**

```
*/2 * * * * /home/student/scripts/disk_report.sh >> /home/student/logs/disk_report_cron.log 2>&1
```

**Root Cause:** The assignment uses /home/student as the example home directory. My VM user has a different name, so /home/student does not exist and cron would not find the script.

**Resolution:** I used the absolute path to my own home directory in both the test and final crontab lines.

**Result:** Syslog shows cron running the script from my home directory, and the script log shows the scheduled runs.

### Issue 2: git init reported an existing repository

**Command:**

```
git init
```

**Root Cause:** The ~/scripts directory became a Git repository in Week 6, when I tracked backup_etc.sh there. Running git init again reinitialized that repository instead of creating a new one.

**Resolution:** Reinitializing does not change existing history, so I kept the repository and committed disk_report.sh into it.

**Result:** git log --oneline shows the two Week 8 commits above the two Week 6 commits.
