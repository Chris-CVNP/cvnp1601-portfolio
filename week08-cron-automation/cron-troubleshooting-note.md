The most frequent issue related to cron failures is that a job will appear in your output from crontab -l; however, there has been no update in the script log. One reason for this is that cron does not execute out of your home directory. Therefore, a relative reference could refer to a completely different location than you expect. Another reason is that cron executes with a very limited environment and PATH, which means a command-line input that works perfectly in your terminal may not be able to find the same program when executed by cron. In addition to both of these reasons, you cannot simply assume the user executing the cron job has permissions to write to the logs directory. You need to include 2>&1 on the crontab line to save error messages somewhere they can be reviewed. A CMD line in either syslog or journalctl indicates that cron attempted to run the job; a timestamped entry in the script log indicates that the script was successful. An example of how to check syslog is as follows: grep CRON /var/log/syslog | tail -20
