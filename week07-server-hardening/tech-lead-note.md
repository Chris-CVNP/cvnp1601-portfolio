I implemented a sequential process to harden the server so I wouldn't remove an access pathway until I replaced it with a proven one. First, I validated the key based login mechanism using the existing ed25519 key pair, which was preinstalled during the VM build. Next, I backed up sshd_config, ensured PasswordAuthentication no and PubkeyAuthentication yes, and reloaded the sshd daemon instead of restarting it. The command line utility sshd -T confirmed that the file contained the directives to disable password authentication and enable public key authentication, and that the resulting effective configuration had password authentication disabled and public key authentication enabled. Because I didn't want to lock myself out due to a bad configuration change, I left the session open and verified a successful public key login from a secondary terminal before proceeding. For the firewall, I configured default deny inbound traffic and allow outbound, created an inbound allow rule for SSH, and then enabled ufw. A verification of the status of ufw via the command ufw status verbose showed that the firewall was activated and that port 22, the SSH service, was permitted. I changed permissions to 700 on both harden.sh and the ~/.ssh directory; additionally, I modified permissions to 600 on ~/.ssh/authorized_keys; and ran ls -la to confirm each modification. Finally, a find audit revealed no items in my home directory with global write permission. The last risk identified in this example is that SSH access is available from any IP address. Limiting SSH access to a specific management network is something that should be escalated to the team lead prior to implementing.
