Three controls were placed into /project. The first control was for Standard Permissions. Standard Permissions were implemented by setting group write with chmod g+w, and then assigning the project to both ************* and developers using chown. This allows the development team to create new files within /project but does not open the entire directory to all users. The second control is the Sticky Bit. The Sticky Bit was enabled using chmod +t. Although everyone in the developers group has permission to write to the /project directory, no developer may delete an item created by another developer. The third control is SGID. An SGID was established by enabling chmod g+s. Any items created as part of this project will have inherited the Developers Group rather than the original Primary Group of the user who created them. As a result, team members can view each other's documents. In addition to these security controls, I added an ACL Entry for Carlos, allowing him Read & Execute. I later removed this ACL Entry. This method allows contractors temporary access to /project with specific scope without having long-term membership in the developers group.
The evidence supporting my assertions comes from the denied actions. When Bob attempted to use rm on alice-file.txt, he received Operation Not Permitted, and the document remained intact. before-sgid.txt had Group alice while after-sgid.txt had Group Developers.
There is a small remaining level of risk because other users hold Read and Execute rights to the /project directory. Clean-up activities include removing the lab accounts; removing the developers group; and removing /project.
