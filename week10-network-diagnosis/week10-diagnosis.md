State: There are two default routes on eth0. One is via 10.0.2.1, metric = 100, and was learned through DHCP. The other is via 10.0.2.254, metric = 50, with no proto dhcp tag, meaning this route was created by hand. The route for the local subnet 10.0.2.0/24 is available. The trainee tried to reach 8.8.8.8 with ping -c 4 8.8.8.8, and the pings timed out with 100% packet loss, so nothing external to the local subnet can be reached. Since there were no references in the transcript about using DNS, it was clearly just a raw IP address.

Root Cause: When two default routes exist, the kernel selects the route with the lowest metric. In this case, the manually added route via 10.0.2.254 at a metric of 50 beats the DHCP route via 10.0.2.1 at a metric of 100, therefore ALL outgoing traffic is going to 10.0.2.254. That network device does not forward traffic to the Internet; therefore each ping times out. Although the trainee is correct when they say there is a default route, it's the incorrect one that is routing all of the traffic.

Remediation: Delete the route that isn't working properly so the DHCP route via 10.0.2.1 becomes the active default route. The trainee needs to enter: sudo ip route delete default via 10.0.2.254. This makes a runtime change; if it came from netplan, then either remove it from netplan or it will come back after a reboot.

Verification: Before doing anything else, validate that the routing choice was made correctly. Check to see how many default routes are currently active: ip route show should only have one default route; check to make sure that the kernel chose to use the DHCP route to send traffic to 8.8.8.8: ip route get 8.8.8.8 should have chosen to use the DHCP route via 10.0.2.1. Once you've validated the kernel is making the correct routing choice for your traffic, verify that actual traffic flow works: ping -c 4 8.8.8.8 should return four replies with zero percent packet loss; traceroute 8.8.8.8 should also indicate that your traffic flow started with 10.0.2.1.

Security Note: Simply having a default route appear in your routing table doesn't mean it's being used to carry traffic when there are multiple default routes; in cases where there are multiple default routes present, the kernel decides based on metric; therefore what appears to be a good route may be completely irrelevant while another route with a lower metric carries all of your traffic to a dead or wrong gateway; ip route get shows you which route the kernel is really using, similar to confirming whether or not a particular firewall rule is active vs relying solely on what appears in a configuration file.
