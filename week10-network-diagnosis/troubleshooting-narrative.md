What went wrong: The ticket stated the server couldn't connect to an outside endpoint, yet upon further investigation, nothing was broken on the server itself. While investigating there were two items identified; one was the traceroute command was not available on the server and the other item identified during the process was that when the ip route add command was used by the student, it created another default route next to the existing DHCP route.

What evidence I checked first: Before changing anything, I captured ip addr, ip route, and ss -tlnp into a timestamped report file located in ~/reports. That report showed that ens18 had an IP address of 10.10.50.103/24 assigned via DHCP, a default route pointing to 10.10.50.1, and sshd listening on port 22. Then I pinged 8.8.8.8 and google.com individually to separate routing from DNS, and both returned four replies for each ping.

What I tried: First, I executed sudo ip route add default via 10.10.50.1 as directed by the assignment. On subsequent execution of that command I received RTNETLINK answers: File exists messages and viewed ip route show output showing two default routes via 10.10.50.1: one being the DHCP-learned route at metric 100 and the second being manually created without a metric. At this point traceroute 8.8.8.8 returned command not found. Therefore, I utilized the apt package manager to install it with sudo apt install traceroute, as specified within the assignment under minimal Ubuntu installation.

What fixed it: Since all necessary protocols were functioning correctly, including routing, DNS, and SSH, no network changes were required. The addition of installing traceroute resolved the missing command.

How I verified the result: Following the addition of the route command, both ping -c 4 8.8.8.8 and ping -c 4 google.com returned four replies with zero percent packet loss; and traceroute 8.8.8.8 displayed 10.10.50.1 as its first hop. Additionally, ss -tlnp and systemctl status ssh demonstrated that sshd remained operational and listening on port 22. Lastly, I generated another post-fix capture using identical commands as those that produced the pre-change captures allowing for direct comparison of both files.

Security or reliability impact: Although the added default route exists in the current kernel, it will cease to exist once the server is restarted and therefore does not represent a long term solution; persistent routes are usually maintained through netplan configuration on Ubuntu. As such until the manual default route is removed, the routing table will remain different than the documented configuration and represents the type of undocumented changes that increase difficulty for auditing potential future outages.
