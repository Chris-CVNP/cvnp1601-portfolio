State
The tar command ran but failed. After running, it printed "Cannot read: Permission denied" when trying to access a file under /etc, which was protected. Then it printed "Exiting with failure status due to previous errors," indicating tar had also exited with a non-zero status value. The script continued to report that the backup operation was successful, "Backup succeeded," along with a time stamp; additionally, the $? variable echoed 0, reporting success to whatever invoked it. Although an archive file exists from the backup operation, ls -lh shows it is only 128 bytes; this is an implausibly small size to contain a full backup of /etc, so the backup is essentially empty.

Root Cause
The if statement does not check tar. Instead, the if checks the complete pipeline, tar -czf "$ARCHIVE" /etc 2>&1 | tee -a "$LOG", and by default, bash takes the exit status of the last command in a pipeline as the exit status of the entire pipeline. In this case, the last command that ran was tee. tee succeeded because it could write and append the text it received. So, the if saw a zero from tee, took the success branch, and did not see tar's failure. As stated above, bash's if is working as intended. It's simply checking the wrong exit code.

Remediation
The first step is to take out the pipe from the if condition so that tar's own exit status is evaluated. To do this, change the condition from if tar -czf "$ARCHIVE" /etc 2>&1 | tee -a "$LOG"; then to if tar -czf "$ARCHIVE" /etc 2>/dev/null; then. This way, if tar fails, the condition fails, the else clause logs "ERROR: Backup failed," and exit 1 stops the script. You also have to run the script as root with sudo, since a normal user can't read all files under /etc.

Verification
First angle, exit code and log: run the fixed script without sudo again. You should now see "ERROR: Backup failed," in both your terminal output and /var/log/backup_etc.log; echo $? should also print 1 rather than 0. Second angle, the archive itself: run the fixed script with sudo. You should now see a success message in your terminal output and that echo $? prints 0. Then check the archive directly to verify it was created and has a realistic size. ls -lh /var/backups/etc should output an archive file in the hundreds of kilobytes range rather than 128 bytes. tar -tzf on this new archive will also show you that files from /etc have been backed up.

Security Note
In many ways, a script with a successful log entry that produces no valid archive is worse than a script that fails loudly, because the successful log entry gives no basis for anyone to be suspicious. The incident response team can trust the message "Backup succeeded" as long as they don't check the archive. They will not know that there was nothing backed up until the next outage occurs and they attempt to recover /etc. At that point, the recovery plan will fail exactly when it is needed. A responder should check whether the backup exists by checking its size and contents, which confirms the backup exists.
