State
systemctl start nginx does not succeed and indicates the control process terminated with an error.
systemctl status nginx shows that the unit is failed with Result: exit-code. The new process, PID 5190, executed ExecStart, and returned an exit status of 1/FAILURE. Journal entries indicate the failure was due to bind to 0.0.0.0:80 failing with error 98, Address already in use, and still unable to bind. Therefore the new nginx cannot be brought up because something else is currently occupying port 80.
curl -I http://localhost will return HTTP/1.1 200 OK with Server: nginx/1.18.0; therefore there exists a real nginx process handling incoming requests.
ss -tlnp displays a socket listening on 0.0.0.0:80, belonging to nginx with PID 1043.
ps shows that PID 1043 has a PPID of 1, is running as www-data, is in S, sleeping, state, was initiated at Tue Jul 21 14:22:03 2026, and is labeled nginx: worker process. There are no entries for a nginx master process.
Root cause
Yesterday's kill -9 killed the nginx master process but left the nginx worker process, PID 1043, running. The worker process has been running continuously since July 21st. Since the parent process of this worker process is dead, the worker process became reparented to PID 1. At some point in the past the worker process took ownership of the socket used to listen on port 80. Now when you try to run systemctl start nginx to bring up a new instance of nginx, binding to port 80 is unsuccessful because the existing worker process is already bound to port 80. The 200 responses are coming from the existing worker process that is still servicing incoming requests using configurations from July 21st. Because of this, today's config changes are also not being applied. Systemd reports that the start operation it was requested to perform was unsuccessful because it attempted to start a new instance of nginx but was unable to successfully bind to port 80, not because nothing is serving.
Remediation
Stop the worker process that currently owns port 80 via the command sudo kill 1043, which sends SIGTERM. Check if port 80 is available after stopping the worker process using the command sudo ss -tlnp | grep :80; this should not return anything. If there is still an entry associated with port 80, and you wish to remove it, use sudo kill -9 1043 as a last resort. After freeing port 80, test your changes against the current configuration using the command sudo nginx -t, and once successful, start the service using the command sudo systemctl start nginx.
Verification
Firstly, verify through the lens of the service manager: systemctl is-active nginx returns active and systemctl status nginx displays information indicating that the service is currently running with a new master process with PID. Secondly, determine what is actively listening and providing services on port 80: The output of the commands sudo ss -tlnp | grep :80 and ps -eo pid,ppid,user,stat,lstart,cmd | grep nginx show that port 80 is now owned by the PID of the new nginx service and includes both a master process and multiple worker processes whose startup times match today's date. Lastly, use curl -I http://localhost again, which should now return a status of HTTP/1.1 200 OK, demonstrating that a brand-new service is now serving requests and executing according to today's configuration.
Security Note
A service manager provides only its opinion regarding each unit it manages. In this case, systemd reported failed, while an orphaned process continued to serve traffic on port 80 outside of systemd's management scope. Had the incident been considered resolved solely on the basis of the status line above or had the HTTP-200 response been dismissed as a caching occurrence, an orphaned process continuing to operate under yesterday's configuration may have remained active on the server. A defendable position requires checking what ports are currently being listened on and who owns them prior to determining what is truly occurring.
