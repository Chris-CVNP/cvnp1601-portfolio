The biggest problem was that the lab server had three issues at one time. nginx wasn't able to start due to a typo in a directive at line 46 of /etc/nginx/sites-enabled/default called server_nmae. /var's usage went from 36% to 42% after a 500MB file was created as /var/log/testfill.img. /var/www/html & its index page were both owned by root:root instead of www-data.
First things I checked.
For nginx I first looked at systemctl status nginx; this gave me information that said Result: exit-code and that also told me how long ago nginx stopped working. Then I took the last 100 lines of log data and put them into a timestamped diagnostic file in ~/reports. For disk I checked df -h /var to see if I had enough free space before I created my testfile. For ownership I checked curl -I http://localhost and ls -la /var/www/html before making any changes.
What I did try.
I tried to run sudo nginx -t to see why nginx wouldn't work. This let me know about the bad directive server_nmae, which should have been server_name, at line 46. Then I tried running sudo systemctl restart nginx. For disk I used sudo du -sh /var/log/* 2>/dev/null | sort -rh | head -5 to figure out what was using the most space inside /var/log. To make sure no other process had the file open, I ran lsof. For ownership I ran sudo chown -R www-data:www-data /var/www/html.
What worked.
Running truncate -s 0 emptied the testfile and got /var back to 36%. After running sudo chown -R www-data:www-data /var/www/html, www-data became the owner of /var/www/html again. Since I didn't fix the nginx directive, nginx continued to fail.
How I confirmed results.
After running truncate, when I ran df -h /var, I saw that I now had 3.3GB being used and 6.0GB still available, just like they were originally. When I ran ls -la /var/www/html, I found that www-data www-data owned the /var/www/html directory and index page. Since nginx failed again, when I ran systemctl is-active nginx, I received a failed message, and since nginx wasn't running, when I ran curl -I, I got a connection failure error.
How it impacted security and reliability.
When nginx was not running, none of our users were able to get onto our website; this is the worst possible outcome. If we didn't correct the issue with disk usage on /var, eventually, /var will run out of space completely and writes will fail. Since write failures can include the writing of logs which are needed for troubleshooting, it is important to monitor these kinds of metrics.
I made sure to use truncate instead of rm so that the space taken up by the testfile isn't wasted. Also, checking lsof before deleting files is an easy way to avoid tying up too much space for an open file. Finally, instead of chmod 777-ing the entire web directory, and thus giving it the ability to be read/written/ran/executed/etc by EVERY user, I ran a scoped chown to prevent anyone but www-data from having permission to write/edit.
