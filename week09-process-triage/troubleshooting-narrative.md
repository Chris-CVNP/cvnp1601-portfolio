What went wrong: The server became slow as a result of a runaway background bash loop, PID 25577, taking one CPU core at 100%; the issue with nginx was that a worker_connections 768 directive in /etc/nginx/nginx.conf did not include a semicolon and therefore the configuration test failed and the service could not come online.
What evidence I checked first: Before doing anything else, I identified the process consuming the most CPU by running the commands ps aux --sort=-%cpu | head -10 and top. I documented the PID, the owner of the process, the percentage of CPU being consumed by the process, and the command used to run the process. In addition, I checked systemctl status nginx and found that the service was failed, Active: failed, due to an exit code. Finally, I reviewed the output of journalctl -u nginx -n 50 --no-pager to confirm that there was an unexpected } in /etc/nginx/nginx.conf:10.
What I tried: I issued SIGTERM to the loop with kill 25577 and checked if it worked using ps aux | grep 25577. As for nginx, I issued two separate restarts of the service at times 16:27:00 and 16:28:25 UTC but each attempt resulted in the same configuration error indicating that simply restarting the service would not resolve this issue.
What fixed it: The loop terminated after receiving its first SIGTERM, thus it was unnecessary to send a SIGKILL. For nginx, I first created a copy of the journal output to ~/reports/diagnosis_20261022_163046.txt. Then, I added back into the file containing the nginx configuration directives the missing semicolon. Next, I validated that my changes were syntactically correct via sudo nginx -t. And finally, I restarted the service with sudo systemctl restart nginx.
How I verified the result: Since ps aux | grep 25577 only returned the grep command itself, I know that the loop has been eliminated. Further, since systemctl is-active --quiet nginx returned nginx is up, I am confident that the service is operational once again.
