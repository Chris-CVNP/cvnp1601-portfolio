State: The ps command executed successfully, identifying the highest CPU usage PID, PID = 5502, at approximately 97.8 percent CPU. User www-data is the owner of the process, the service account the nginx service runs under. The -bash process and the trainee prompt indicate that the current login session belongs to trainee. Both attempts to use kill 5502 and kill -9 5502 resulted in an Operation not permitted error message indicating the trainee could not deliver a signal to the process. Therefore, the process is still running.
Root Cause: The trainee cannot send a signal to a process belonging to another user ID. In Linux, only a privileged user, such as root, can send signals to a process belonging to another user ID. A non-privileged user can only send signals to processes belonging to their own user ID. Since the process identified by PID = 5502 belongs to the www-data user ID, not to the trainee's user ID, the kernel rejected both signals prior to delivering them. SIGKILL is subject to permission restrictions just like all other signal types. It does not allow a signal to be sent when permission is denied, but instead determines what happens to the process once the signal has been delivered.
Remediation: Send the same SIGTERM using escalated privileges via sudo kill 5502. Then check whether the process has terminated, and only if it is still running escalate via sudo kill -9 5502. A reboot is not required to complete this task.
Verification: Use two methods to verify this solution. First, run ps aux --sort=-%cpu | head -3 again to confirm PID = 5502 is no longer listed in the results, and verify that no other process is currently utilizing CPU at that level. Second, verify that the web service is still operating normally via systemctl status nginx. If the service continues to report itself as active, then the removal of the runaway worker did not take the web service down.
Security Note: An Operation not permitted error indicates that the kernel performed a permission check and determined that access should be denied. This indicates that the kernel checked who attempted to send the signal against who owns the target process, and found that the trainee does not possess sufficient rights to signal a process owned by www-data. Failure to recognize a permission boundary can result in failure to properly terminate a process. Additionally, treating a permission boundary as a sign that a process is unkillable can lead to improper actions such as rebooting, resulting in dropping all connections on the server and delaying resolution to an issue that requires only sudo.
